# HackTX Trip Planner: Handoff

Read this before changing anything. It replaces the older `HACKTX_HANDOFF.md` (that one stops at Phase 7.5 and is out of date).

**One sentence:** an AI group trip planner. Everyone enters their own city, budget, interests and free dates; Muse Spark turns that into three options, the group votes, Muse builds one shared itinerary and works in the dissent, and real places, hotels and flights fill it in. Existing AI plans *my* vacation. This plans *our* vacation.

## 2. Rules that must not be broken

- **Humans do all Git.** AI agents edit local files only. No `git add`, commit, push, branches, PRs. (One slip happened: a stray `git rm --cached` was undone immediately.)
- All external API calls are **server-side only**. Keys never reach the browser.
- Muse reasons; SerpApi supplies live facts. **Muse must never invent prices, flights or hotel availability.**
- Booking is **simulated**. Never imply a real purchase unless an assistant recorded one (it is then tagged "By your assistant").
- Everything Muse returns passes **strict JSON schema + server validation** before it is saved. Never trust raw model output.
- Manual availability is the MVP. Google Calendar is a stretch, so don't claim it exists.

## 3. Stack

Next.js 16.4 (App Router, Cache Components), TypeScript, Tailwind 4. Node 24 locally.
**Next 16 is not the Next you know:** read `node_modules/next/dist/docs/` and `AGENTS.md` before writing Next code. Dynamic route handlers use `RouteContext<"/path/[id]">` and pages use `PageProps<"/path">`; those types are generated by `next dev`/`next build`, so a fresh route shows a type error until one of them runs.

| Concern | Service |
| --- | --- |
| Reasoning | Muse Spark via the Meta Model API (`https://api.meta.ai/v1/chat/completions`, model `muse-spark-1.3`, strict `json_schema`) |
| Places, reviews, hotels, flights | SerpApi: `google_maps`, `google_maps_reviews`, `google_hotels`, `google_flights` |
| City ids for flights | Wikidata (free), Freebase id like `/m/0vzm` |
| Photos for options/stops | Wikipedia search API (free), then SerpApi Google Maps thumbnails as fallback |
| City autocomplete | Photon / OpenStreetMap (free) |
| Storage | Supabase Postgres, one JSON document per trip, optimistic locking. Falls back to `data/trips.json` with no credentials |
| SMS codes | Twilio Verify (demo mode shows the code on screen if keys are missing) |

| --- | --- |

| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Must be the **secret** key (`sb_secret_…`). The publishable key fails with a row-level-security error. `db:check` flags this |

## 5. Architecture in one pass

```
Trip (one JSON doc in Supabase)
 ├─ travelers[]  (prefs, availability, avatar, phoneHash, assistantTokenHash)
 ├─ sketch            ← Muse, from the host's description
 ├─ candidateOptions[3] ← Muse (+ photos), votes[]
 ├─ itinerary         ← Muse compromise; days[], overrides[] (personal plans), places from SerpApi
 ├─ chat[]            ← feedback + Muse replies
 └─ travel            ← hotels, flights per traveler, bookings per traveler
```

- **Invalidation:** `clearPlanningOutputs()` in `trip-updates.ts` wipes options, votes, itinerary, chat and travel together whenever planning inputs change (new traveler, prefs, availability, trip details). Add any new derived field there.
- **Storage layer:** `trip-repository.ts` is the only thing routes talk to. It calls `store.update(tripId, mutate)`. The Supabase store retries on version conflicts and retries reads once on cancelled requests. Never read-modify-write outside `update`.
- **One-time paid work uses a claim pattern** (`claim…`/`finish…` in the repository with a `pending` status and a 2 to 3 minute timeout) so two viewers never run the same SerpApi search: itinerary places, option photos, hotel search, flight search, trip sketch.
- **Planners are swappable:** each Muse feature has an interface plus a `Mock…` and `Muse…` implementation, chosen in `candidate-planner-factory.ts` (candidate planner, itinerary planner, reviser, sketch planner). All Muse HTTP goes through `muse-client.ts`.
- **Live updates:** `/api/trips/[id]/stamp` returns a hash of the trip; `LiveRefresh` polls it every 4s and calls `router.refresh()`. The itinerary page polls its own state endpoint. Not websockets.
- **Identity:** a traveler is a UUID remembered in `localStorage` per trip (`hacktx-trip-planner:traveler:<tripId>`). It is convenience, not security. Optional phone sign-in (Twilio code → signed cookie `tp_session`) lets someone restore their travelers on a new device through `/my-trips`.

## 7. MCP assistant connector

`POST /api/mcp` is a stateless Streamable-HTTP MCP server. A traveler creates a token on `/trip/[id]/connect` (shown once; only a keyed hash is stored) and sends `Authorization: Bearer <token>`. A token sees **only its own traveler's view**.

Tools: `get_my_trip`, `get_my_bookings`, `get_booking_details`, `mark_booked` (records a booking the traveler approved and the assistant completed). Verified live with `initialize`, `tools/list`, each tool, and 401/unknown-tool errors.

**Unverified:** whether the Muse app accepts custom MCP connectors at all, or needs OAuth. Any MCP client that sends a URL + Bearer header works. The server only helps assistants that can reach it, so it needs deployment, not `localhost`.

## 9. Known limits and gotchas

- Dev server can serve **stale modules or missing Tailwind classes** after many edits (this caused "is not a function" and unstyled-element reports). Restart `npm run dev` first when something looks impossible.
- `npm run build` rewrites generated route types, so run it once after adding a route to clear phantom type errors.
- Travel times between stops are straight-line estimates (×1.3), not routing.
- Flight prices are Google's round-trip price shown for the outbound leg; the return flight isn't chosen separately.
- Option generation takes about 45 s (Muse), then day-header photos load in the background (Wikipedia, then SerpApi for gaps). Candidate activity rows use local icons, with roughly one header image per candidate/day.
- A trip's itinerary photos use SerpApi thumbnails; approximately 20 to 35 searches the first time an itinerary opens.
- Stop photos from Wikipedia can miss; the fallback is a time-of-day icon.
- Anyone with a trip link can act as an unsaved traveler. Phone sign-in only protects *saved* travelers' ability to restore themselves.
- In-memory pieces that reset when the server restarts: demo SMS codes and phone rate limits. Fine for a demo, not for multi-instance production.
- Supabase `findByTraveler` uses JSON containment; add a GIN index on `data` if the table gets large.

## Current polish and revision behavior

- Ordinary group chat only saves messages. Muse runs only when a trimmed message begins with the @muse mention (case insensitive).
- Minor shared edits and personal alternatives remain supported. Destination changes, whole-trip replacement and substantial multi-day rewrites become one pending proposal instead of applying immediately.
- Every currently joined traveler must vote. A strict approval majority applies atomically against the original itinerary id/revision; ties reject, and stale proposals cannot overwrite newer work.
- Approved moves update trip destination/name and itinerary title/destination/days, clear old real-place matches and personal plans, clear travel searches/bookings, and show an approval notice. Same-city major edits preserve only unchanged personal stops.
- Major-change votes require a signed browser proof from create/join or the traveler's existing verified saved phone. The demo seed script prints a signed proof with each console identity command; rerun it for a newly seeded demo. Old localStorage-only identities without a saved phone cannot securely prove ownership and cannot vote without trusted recovery; they can still save and restore their phone. Their normal planning/chat access still works.
- Phone saving/restoration remains compatible. A newly linked phone only gains voting access when the browser already has valid voter proof; an unsigned first-time phone save is tagged phoneVotingVerified false and cannot grant someone else's vote. Existing previously saved-phone restoration through My Trips is preserved.
- Preferences show one total budget and one combined final notes field. Legacy optional budgets survive edits, and legacy destination notes are combined without duplication.
- Availability supports mouse/pen painting, keyboard clicks and touch taps. Options over seven days use seven-day dialogs. The avatar editor uses a viewport-bounded native dialog.
- Progress has four blue stages: Get Ready, Itinerary Options & Vote, Shared Itinerary, Book Travel.
- Travel keeps its existing airline logos, adds Cheapest/Shortest badges, distinguishes hotel shares from simulated charges, and offers an honest mailto email draft/copy action.
- Early availability flight-price hints remain deferred; no new automatic paid searches or Expedia provider were added.
- Browser-based manual desktop/mobile QA could not be completed in the implementation session because no browser surface was available. Run the requested interaction checklist before presenting.
